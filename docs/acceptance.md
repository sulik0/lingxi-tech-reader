# 本阶段验收记录

日期：2026-10-10（北京时间）。本文区分代码检查、本机真实数据和线上验证，未成功的步骤不记为通过。

## 已观察到的真实结果

本机使用实际公开订阅、SQLite 与正式业务模块：极客公园解析并首次保存 30 篇，IT之家解析并首次保存 50 篇；重复读取新增 0 篇。宝玉博客旧地址返回 301，最终地址可读取但没有符合最近 14 天条件的文章。真实正文与分析留在忽略的 work/acceptance，不提交 Git。

DeepSeek 使用 `https://api.deepseek.com`、`deepseek-v4-flash`。凭据仅在本地隐藏文件和 Sites Secrets。首次真实模型分析因单篇事实被错误标为来源一致而被校验拒绝，未发送。已针对这个实际问题加强约束并加入一次有限重试；后续结果继续记录。

## 数据路径

RSS/Atom → 正文与规范 URL → D1 feed_articles 与永久去重记录 → 模型比较新文章和近期事件 → 检查正文证据 → reading_events → 工作台与每日简报 → 冻结正式正文与已纳入文章 → 渠道发送记录。

没有模型时自动文章也会形成待分析事件，正常用户无需手动导入。手动调试数据不参与正式简报。

## 验证范围

自动测试使用真实 SQL 和自编内容，检查跨天、迟到、历史去重、预览不发送、重复触发、飞书签名、机器人不确定状态以及分组修正。它们不能证明人工聚类质量、外部真实性、用户实际收到消息或连续多天稳定运行。

公开来源读取与真实模型是分别验证的。本机 curl 成功不表示 Worker 出站网络成功。只有正式平台发布成功并读回线上数据，才能记为部署与线上采集通过；构建中的 Cron 字段不能证明平台已注册定时任务。

## 三个来源共同失败的原因与修复

在实际 Workerd 运行环境调用采集接口，重现了 `TypeError: Invalid redirect value`：该环境只接受 `follow` 或 `manual`，而原采集代码传入 `error`，因此尚未连接来源就失败。Node.js 模拟测试支持这个选项，没有发现这一运行环境差异。

订阅请求已改用 `manual`，收到 3xx 时明确报错，不跟随新地址；允许域名、HTTPS 和证书检查继续保留。三种推送共用的发送函数也存在同样写法，已同步修改；发送遇到 3xx 时记为无法确认，不盲目重发，也不向新地址转发凭据和正文。新增两项回归测试，当前共 30 项测试、类型检查与构建通过。

本次平台配置读回显示任务实际为每 5 小时一次，已与最初每小时的保存记录不同；保留当前平台配置，没有擅自改回。应用仍按北京时间判断是否到每日发送时间，实际发送需等待下一次任务执行。

修复后的线上采集结果需要单独读回，不能仅据本地重现与测试通过写成线上新增文章成功。本机直接访问私人站点另外遇到证书验证失败，没有关闭 TLS 检查。

修复版本已部署成功，代码提交 `a34e161` 的 GitHub CI 通过。在本地实际 Worker 中，第一轮极客公园新增 30 篇；随后使用与线上一致的三个地址读取，D1 读回极客公园 30 篇、IT之家 50 篇，宝玉博客请求成功但最近 14 天内无符合条件的条目。三个启用来源的最近成功时间均已更新且错误为空。这是实际 Workerd 请求结果，不是 Node 模拟响应。

第二轮本地采集后的模型处理被构建引起的开发 Worker 重启中断，不能记作完整分析通过；已入库文章仍保留。第一轮模型处理也记录了不同事件、引文不匹配和格式不完整的拒绝结果，未伪造分析或发送。线上脚本受证书错误阻挡，两个现有页面的自动化读取也超时，已请求通过已登录页面的“检查新文章”触发一次，再读回平台数据完成线上复验。
